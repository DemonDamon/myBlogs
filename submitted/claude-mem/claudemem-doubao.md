# Claude-Mem：AI 编程助手持久化记忆系统技术调研报告

## 引言：AI 编程助手的 "失忆" 痛点与 Claude-Mem 的诞生

在 2025 年的编程世界中，AI 编码助手已成为开发者日常工作中不可或缺的伙伴。然而，随着项目复杂度的不断增加，这些智能工具正面临着一个根本性的 "认知危机"——**上下文限制导致的记忆碎片化、无关代码污染带来的逻辑错乱，以及频繁对话中的知识遗忘**。这些问题不仅影响开发效率，更可能引入难以察觉的安全隐患。

当前主流 AI 编程工具面临着严格的上下文限制，通常只能处理 4K-128K tokens 的输入，这就像一个 "记忆牢笼"。在这个有限的空间内，AI 编程助手表现出三个核心问题：**信息截断**导致当对话超过上下文窗口时，早期关键信息被无情丢弃；**优先级错乱**使模型无法区分核心 API 与无关注释，重要代码被挤出上下文；**理解断层**让跨多个文件的复杂逻辑被割裂，AI 只能看到代码 "碎片"。

更为严重的是，AI 编程助手在长时间对话中会 "忘记" 先前确定的重要约定。架构决策可能在 20 分钟后就被完全忽略，精心制定的命名规范在后续生成中被违反，核心需求在多次交互后逐渐失真。这种 "失忆症" 在实际开发中造成了巨大的困扰：开发者需要在每个新会话开始时重新向 AI 解释项目背景、当前进度和接下来的计划。

市场数据显示，全球 AI 代码工具市场正经历着爆发式增长。2024 年全球市场规模达到 61.11 亿美元，预计到 2030 年将增长至 260.33 亿美元，年复合增长率高达 27.1%。中国市场同样增长迅猛，2023 年市场规模为 65 亿元人民币，预计 2028 年将达到 330 亿元，年复合增长率为 38.4%。然而，这种快速增长背后，**跨会话记忆缺失**已成为制约 AI 编程助手进一步发展的关键瓶颈。

在这样的背景下，Claude-Mem 应运而生。作为一个专为 Claude Code 打造的开源插件，Claude-Mem 的核心功能可以用一句话概括：**自动捕获、压缩并保存你与 Claude 的所有编程会话，让 AI 助手在跨会话时保持上下文连续性**。该项目由 Alex Newman（@thedotmack）开发，截至 2026 年 2 月已获得超过 27.7k 的 GitHub 星标和 1.9k 的 Forks，充分证明了其在开发者社区中的受欢迎程度。

Claude-Mem 的出现，标志着 AI 编程助手从 "一次性对话工具" 向 "长期协作伙伴" 的重要转变。它通过创新的技术架构和设计理念，不仅解决了传统 AI 编程助手的 "失忆" 问题，更为整个行业的发展指明了方向。

## 一、Claude-Mem 核心功能解析

### 1.1 持久化记忆：跨会话的知识传承

Claude-Mem 的核心价值在于为 Claude Code 提供了真正意义上的**跨会话持久记忆能力**。与传统 AI 编程助手每次启动都是 "全新大脑" 的情况不同，Claude-Mem 通过自动捕获、AI 压缩、智能检索三个步骤，实现了跨会话记忆保持，能够自动记录所有工具调用和代码操作。

这种持久化记忆的实现机制是多层次的。首先，系统通过**生命周期钩子**捕获关键事件，包括会话启动、用户提问、工具执行、会话结束等关键时刻。当你在 Claude Code 中执行文件读写、代码编辑、命令执行等操作时，系统都会自动捕获这些行为并生成 "观察记录"（Observations）。这些观察记录不仅包含了操作的原始数据，还通过 AI 算法提炼出了结构化的信息，包括操作类型、关键元数据和核心内容。

更重要的是，Claude-Mem 的记忆具有**强持久性**。即使执行了 /clear 命令，项目的核心记忆也不会丢失。这意味着开发者可以在不同时间、不同设备上继续之前的工作，而无需重新建立上下文。一位开发者分享了这样的使用体验："周一发现权限模块有 Bug，查到一半下班了。周三打开 Claude，直接说 ' 继续昨天的权限问题，完成导出功能 '，它真的接上了。这种 'AI 帮你翻历史 ' 的能力，比搜聊天记录快太多了"。

### 1.2 渐进式披露：智能的信息呈现策略

渐进式披露（Progressive Disclosure）是 Claude-Mem 最巧妙的设计之一。这个策略的核心思想是：**不是一股脑把所有历史记录塞给 AI，而是分层展示信息**。这种设计借鉴了前端开发中的懒加载思想，在保证信息完整性的同时，最大限度地节省了宝贵的 token 资源。

Claude-Mem 实现了**三层渐进式披露架构**：

**第一层：索引层（Index）**

当用户或 AI 需要搜索记忆时，首先返回一个紧凑的索引，包含观察点的 ID、标题、类型、时间等元数据。每个结果仅占用 50-100 个 token，允许在有限的上下文窗口内展示大量结果。这种设计让用户能够快速浏览历史记录的概览，定位到感兴趣的内容。

**第二层：时间线层（Timeline）**

当用户识别出感兴趣的观察点后，可以获取该观察点周围的时间线上下文。时间线展示了在特定时间点前后发生的事情，帮助理解观察点的背景和后续发展。这一层的设计特别适合需要理解事件因果关系的场景，比如追踪 Bug 修复的完整过程。

**第三层：详情层（Details）**

只有在确认需要深入了解某个观察点时，才获取完整的观察点详情，包括所有字段的完整内容，每个详情约占用 500-1000 个 token。这种设计确保了只有真正需要的信息才会被加载，避免了信息过载。

通过这种分层策略，Claude-Mem 在常规使用场景下能够节省约**90% 的 token 消耗**，而在 "无尽模式" 下，最高可以节省**95% 的 token**，工具调用次数上限提升约 20 倍。这意味着开发者可以用同样的预算让 AI 助手处理更长时间的复杂任务。

### 1.3 智能搜索：自然语言驱动的记忆检索

Claude-Mem 内置了强大的**mem-search 技能**，支持通过自然语言查询项目历史。这个技能的独特之处在于，它会在用户提问时自动触发，无需手动调用。当你在 Claude Code 中输入一个问题时，UserPromptSubmit hook 会自动触发语义搜索，把 top-3 相关记忆注入到上下文中。

mem-search 技能支持**10 种不同的搜索模式**：



* 全文搜索观察记录

* 按会话摘要搜索

* 按用户提问搜索

* 按概念标签搜索（discovery/problem-solution/pattern）

* 按文件名搜索

* 按操作类型搜索（decision/bugfix/feature/refactor）

* 混合搜索（语义 + 关键词）

这种多样化的搜索能力让开发者能够以最自然的方式与历史记忆交互。例如，你可以直接问："上周我重新设计过登录流程，当时用了什么鉴权策略？"，AI 会自动检索相关的历史记录并返回答案。每个答案都带有引用来源，可追溯到原始操作记录。

搜索系统的技术基础是**混合检索策略**，结合了 SQLite FTS5 的全文检索和 Chroma 向量数据库的语义搜索能力，通过 RRF（Relevance Ranking Fusion）算法融合排序，提供最佳的搜索结果。这种设计既保证了关键词搜索的精确性，又具备了语义理解的灵活性。

## 二、技术架构深度剖析

### 2.1 生命周期钩子：全方位的交互捕获

Claude-Mem 采用观察者模式，通过精心设计的**5 个核心生命周期钩子**在不干扰主会话的前提下捕获关键事件。这些钩子形成了一个完整的交互捕获网络，确保不会遗漏任何重要的开发信息。

**1. SessionStart Hook**

会话启动时触发，负责从 Worker 服务获取之前会话的上下文摘要，并将其注入到当前会话中。这是实现跨会话记忆的关键入口。当你打开一个新的 Claude Code 会话时，这个钩子会自动工作，让 AI"记起" 之前的工作内容。

**2. UserPromptSubmit Hook**

在用户提交提示时触发，负责记录用户的问题，并触发 Worker 服务开始处理可能的观察点提取。这个钩子不仅记录了用户输入的内容，还会分析问题的意图，为后续的智能搜索提供基础。

**3. PostToolUse Hook**

在 Claude 使用工具后触发，捕获工具的使用情况，包括工具名称、输入参数和输出结果。这是观察点提取的主要数据源。每当 Claude 执行文件读取、代码生成、命令执行等操作时，这个钩子都会捕获相关信息。

**4. Stop Hook**

在会话暂停或结束时触发，负责触发会话总结生成。这个钩子确保了即使在异常终止的情况下，已完成的工作也能被保存下来。

**5. SessionEnd Hook**

在会话完全结束时触发，执行清理工作。这个钩子会生成最终的会话摘要，并确保所有数据都被正确持久化。

值得注意的是，除了这 5 个核心钩子外，还有一个**Smart Install 预检查脚本**，它会在安装或启动流程中运行，负责检查和安装必要的依赖（如 Bun、uv 等）。所有钩子都被设计为轻量级的 HTTP 客户端，v7.0 重构后每个钩子仅约 75 行代码，它们只负责向 Worker Service 发送请求，不做任何重计算，以确保不会拖慢 Claude Code 的响应速度。

### 2.2 双数据库存储：结构化与语义化的完美结合

Claude-Mem 采用了创新的**双数据库存储架构**，结合了 SQLite 和 Chroma 两种不同类型数据库的优势，实现了结构化数据存储与语义搜索的完美结合。

**SQLite 数据库**作为主要的关系型数据存储，使用 bun:sqlite 驱动，存储会话元数据、观察点、会话总结、用户提示等结构化数据。数据库位于用户主目录下的～/.claude-mem/claude-mem.db。SQLite 的选择基于以下考虑：



* 零配置，单文件存储，易于备份和迁移

* 支持事务，确保数据一致性

* FTS5 扩展提供高效的全文搜索能力

* 资源占用低，适合桌面应用

**Chroma 向量数据库**作为向量存储，用于语义搜索。Chroma 存储了观察点和总结的向量嵌入，支持基于语义的相似度搜索，数据存储在～/.claude-mem/chroma/ 目录。Chroma 的优势包括：



* 专为向量搜索设计，语义搜索效果优异

* 支持多种嵌入模型

* 可扩展性好，适合大规模数据

* 与 SQLite 结合形成混合搜索（关键词 + 语义），显著提高召回质量

这种双后端设计的核心优势在于**互补性**：SQLite 提供高效的结构化查询和事务支持，适合处理精确查询和关系型数据；Chroma 提供强大的语义搜索能力，能够理解查询的意图，找到语义相关但关键词不完全匹配的内容。SearchManager 会根据查询类型智能选择合适的后端，或者在需要时进行混合搜索。

为了保证数据一致性，Claude-Mem 实现了**双写策略**：



```
async storeObservation(observation: Observation): Promise\<void> {

&#x20; // 1. 同步写入SQLite（事务保证）

&#x20; const id = await this.withTransaction(async (db) => {

&#x20;   return this.sessionStore.storeObservation(db, observation);

&#x20; });

&#x20; // 2. 异步写入Chroma（不阻塞主流程）

&#x20; this.chromaSync.storeEmbedding(id, observation).catch(error => {

&#x20;   logger.error('Failed to store Chroma embedding', error);

&#x20; });

}
```

这种设计确保了即使 Chroma 写入失败，SQLite 中的数据依然完整，保证了系统的可靠性。

### 2.3 Worker 服务：智能的后台大脑

Worker 服务是 Claude-Mem 的**核心业务逻辑层**，它是一个独立的 HTTP 服务，运行在本地 37777 端口（可配置），使用 Bun 作为运行时。这个服务采用了领域驱动设计（Domain-Driven Design）思想，将功能划分为多个领域服务。

**Worker 服务的核心组件包括**：

**SessionManager**负责管理会话的生命周期，包括会话的创建、激活、暂停和销毁。它维护着内存中的会话状态，并协调各个 Agent 的工作。这个组件确保了多会话场景下的状态隔离和数据安全。

**SDKAgent**基于 Claude Agent SDK 的 AI 处理 Agent，负责使用 Claude 模型进行观察点的智能提取和会话总结生成。这是系统的 "大脑"，决定了哪些信息值得被记住。除了 SDKAgent，系统还支持 GeminiAgent 和 OpenRouterAgent，提供了灵活的 AI 处理能力。

**SearchManager**负责所有搜索相关的业务逻辑，包括全文搜索、语义搜索、时间线查询等。它协调 SQLite 和 Chroma 两种存储后端，实现混合搜索策略。这个组件是连接存储层和应用层的关键桥梁。

**SSE Broadcaster**提供实时事件广播功能，通过 Server-Sent Events 向 Web UI 推送实时的记忆流数据。这使得开发者可以在[http://localhost:37777](http://localhost:37777)实时查看记忆的变化。

Worker 服务的启动采用了**两阶段模式**：第一阶段快速启动 HTTP 服务并绑定端口，把控制权还给 Hook 以防止超时；第二阶段在后台进行初始化，包括数据库连接、崩溃恢复、SearchManager 建立、MCP 连接等耗时操作。这种设计确保了系统的响应速度和稳定性。

## 三、核心技术亮点

### 3.1 三层检索工作流：革命性的记忆访问模式

Claude-Mem 的三层检索工作流是其最具创新性的技术亮点之一。这个工作流通过精心设计的三个步骤，实现了**约 10 倍的 token 节省**，同时保证了信息检索的准确性和效率。

**第一步：Search（搜索索引）**

使用 search 工具进行自然语言或关键词搜索，返回一个紧凑的索引列表。每条结果包含 ID、标题、类型、时间戳等元数据，仅占用约 50-100 个 token。这个步骤的设计理念是让用户能够快速浏览大量历史记录的概览，定位到感兴趣的内容。例如，当你搜索 "authentication bug" 时，会立即得到一个包含相关修复记录的列表。

**第二步：Timeline（时间线上下文）**

使用 timeline 工具获取特定观察点前后的时序上下文。这个工具会展示围绕某个观察点或查询的时间顺序信息，帮助理解事件的因果关系和发展脉络。例如，当你找到一个关于认证 Bug 修复的记录后，可以通过 timeline 查看修复前后的相关操作，了解整个修复过程。

**第三步：Get\_Observations（获取详情）**

使用 get\_observations 工具根据筛选出的 ID 批量获取完整的观察记录详情，每条记录占用约 500-1000 个 token。这个步骤只会在你确认需要深入了解某个记录时才被调用，避免了不必要的 token 消耗。

这个三层工作流的设计遵循一个重要原则：**Never fetch full details without filtering first（永远不要在过滤前获取完整详情）**。这个原则通过一个特殊的\_\_IMPORTANT 工具传达给 AI，确保其在使用记忆系统时也遵循高效的检索模式。

为了进一步优化检索效率，Claude-Mem 还提供了**save\_memory 工具**，允许开发者主动写入重要的记忆信息。例如，你可以使用以下命令记录 API 认证的要求：



```
save\_memory(text="API requires auth header X-API-Key", title="API Auth")
```

这种主动记忆机制特别适合记录项目中的重要约定、架构决策等需要长期保存的信息。

### 3.2 AI 驱动的语义压缩：智能的信息提炼

AI 驱动的语义压缩是 Claude-Mem 实现高效存储和检索的关键技术。系统使用**Claude Agent SDK**作为核心的 AI 处理引擎，将冗长的原始工具输出压缩成约 500 个 token 的结构化观察记录。

压缩后的观察记录采用了精心设计的结构化格式，包含以下关键字段：



* **type**：观察点类型，如 decision（决策）、bugfix（Bug 修复）、feature（功能）、refactor（重构）、discovery（发现）、change（变更）

* **title**：简短的标题，概括观察点的核心内容

* **subtitle**：副标题，提供补充说明

* **facts**：事实列表，以 JSON 数组形式存储关键事实信息

* **narrative**：叙述性描述，提供更详细的背景信息

* **concepts**：概念标签，用于分类和搜索

* **files\_read**：读取的文件列表

* **files\_modified**：修改的文件列表

* **discovery\_tokens**：发现该观察点所消耗的 token 数，用于 ROI 分析

这种结构化设计带来了多重优势：



* **信息密度高**：通过分类和标签，可以在有限的空间内传达更多信息

* **可搜索性强**：不同类型的信息可以被独立搜索和过滤

* **可压缩性好**：结构化的数据更容易被 AI 模型理解和压缩

在 Endless Mode（无尽模式）下，这个压缩机制发挥了更大的作用。PostToolUse Hook 会在每次工具调用后阻塞等待（最长 110 秒），让 AI 代理把完整的工具输出压缩成约 500 个 token 的观察记录，然后用压缩后的观察替换原始输出注入回上下文。这种设计将 token 消耗从 O (N²) 降为 O (N)，使上下文窗口内的 token 减少约 95%，工具调用次数可以增加约 20 倍。

### 3.3 隐私控制机制：安全与便利的平衡

在当今注重数据安全的环境下，Claude-Mem 提供了**精细的隐私控制机制**，让用户能够完全掌控哪些信息被记录和存储。

系统实现了**双标签隐私控制系统**：

**1.&#x20;**`<private>`**标签（用户级隐私控制）**

用户可以在提示中使用`<private>...</private>`标签包裹敏感内容，这些内容将不会被持久化存储。例如：



```
请帮我检查这段代码：

\<private>

API\_KEY=sk-xxx  # 不会被系统记录

\</private>

其他部分可以正常记录。
```

这个机制特别适合保护 API 密钥、密码、商业机密等敏感信息。Hook 层会在将数据发送到 Worker 之前，自动剥离这些标签及其内容，确保敏感信息不会进入存储层。

**2.&#x20;**`<claude-mem-context>`**标签（系统级递归防护）**

当 Claude-Mem 向 Claude 注入上下文时，会使用这个标签包裹注入的内容：



```
\<claude-mem-context>

\[注入的上下文内容]

\</claude-mem-context>
```

这个标签的作用是防止 Claude 将注入的上下文再次作为观察点存储，避免递归存储和数据膨胀问题。

隐私控制的实现遵循 \*\*"最小权限原则"\*\*，标签剥离发生在 Hook 层（边缘处理），在数据到达 Worker 和存储层之前完成。系统还实现了 ReDoS 防护机制，使用 MAX\_TAG\_COUNT 限制标签数量，防止恶意输入导致的正则表达式回溯攻击。

除了标签系统，Claude-Mem 还采用了**本地存储策略**，所有数据都存储在用户本地目录～/.claude-mem/ 下，不上传到任何云服务。Worker 服务只监听 127.0.0.1，外部无法访问，确保了数据的安全性。

## 四、工程落地风险点

### 4.1 本地数据库性能瓶颈

尽管 SQLite 在轻量级应用中表现出色，但在 Claude-Mem 的实际应用中，**本地数据库性能瓶颈**仍是一个需要重视的风险点。

SQLite 的性能限制主要体现在以下几个方面：

**高并发写入性能差**是最突出的问题。SQLite 使用库级写锁，当并发写入超过 100 次 / 秒时就可能出现瓶颈。在高并发写入场景下（如秒杀、批量导入），容易出现锁竞争，写入延迟会显著上升，无法像 MySQL、PostgreSQL 那样通过分库分表、分布式事务轻松应对。

**数据库文件大小限制**也是一个潜在风险。虽然 SQLite 理论上支持最大 281TB 的文件大小，但当数据库文件达到 10-100GB 的大型规模，特别是超过 100GB 的超大型规模时，性能可能会受到显著影响。对于长期使用 Claude-Mem 的大型项目，累积的历史数据可能达到相当大的规模。

**复杂查询性能较弱**是另一个问题。对于多表关联、子查询嵌套、聚合分析等复杂 SQL，SQLite 的执行效率远不如专业关系型数据库，不适合大数据量的实时分析场景。虽然 Claude-Mem 的查询相对简单，但在处理大量历史数据时仍可能遇到性能问题。

为了缓解这些问题，建议采取以下措施：



* 定期清理不再需要的历史记录

* 对常用查询字段建立索引

* 采用批量写入方式减少锁竞争

* 对于超大型项目，考虑使用更专业的数据库解决方案

### 4.2 记忆碎片化导致的检索噪声

记忆碎片化是 Claude-Mem 在实际使用中可能遇到的另一个重要问题。当积累了大量历史记忆后，**记忆的碎片化可能导致检索结果中出现大量噪声**，影响开发效率。

这个问题的表现形式包括：



* **过时信息干扰**：Claude 可能检索到过时的信息，比如 "用 Redis 做缓存" 这样的旧方案，而开发者已经切换到了其他技术栈

* **规则冲突**：开发者发现 Claude 开始犯诡异的错误，明明设定过的规则却时而遵守时而违背

* **项目间污染**：如果不清理 Claude-Mem，新项目的 Claude 会被旧项目的思维方式影响

为了避免记忆碎片化带来的问题，需要注意以下几点：



* **定期维护记忆库**：删除不再相关的历史记录，特别是已经被替代的技术方案

* **使用标签分类**：为不同项目或不同类型的记忆添加标签，便于过滤和管理

* **设置合理的检索阈值**：调整相关度阈值，确保只返回真正相关的记忆

* **项目隔离**：为不同项目使用独立的记忆空间，避免相互干扰

### 4.3 钩子函数过滤逻辑误判

虽然 Claude-Mem 的钩子系统设计精巧，但在复杂的开发环境中，**钩子函数的过滤逻辑仍可能出现误判**，导致重要信息被遗漏或无关信息被错误记录。

可能的误判情况包括：



* **上下文窗口限制**：长项目只能塞一部分历史进去，越用越乱；为了省 token，开发者不敢 "什么都扔进去"

* **复杂场景下的信息遗漏**：在极端复杂场景下（比如几十个相关模块、跨多团队改动），摘要可能会出现信息遗漏或侧重点不太符合预期的问题

* **工具调用识别错误**：某些特殊的工具调用可能被错误分类或完全忽略

为了减少误判，可以考虑：



* 仔细配置钩子的过滤规则，明确哪些工具调用需要记录

* 使用多个维度的分类标签，提高信息的准确性

* 定期检查和验证记录的信息质量

* 根据项目特点调整上下文注入阈值，避免过度检索

### 4.4 多项目记忆隔离失效

在实际开发中，开发者通常会同时处理多个项目，**多项目记忆隔离的可靠性**是一个关键的安全和效率问题。

潜在的风险包括：



* **项目间数据泄露**：不同项目的敏感信息可能相互泄露，特别是在使用共享开发环境时

* **开发环境混乱**：如果不清理记忆，新项目会被旧项目的技术栈和约定影响，导致开发环境混乱

* **权限管理复杂**：在团队协作场景下，如何确保不同项目的记忆被正确隔离和授权访问

为了确保多项目记忆隔离的有效性：



* **使用独立的配置文件**：为每个项目使用独立的～/.claude-mem 配置目录

* **项目级标签管理**：在记忆记录中明确标注项目 ID，便于隔离和检索

* **访问控制**：在团队环境中，实现基于角色的记忆访问控制

* **定期清理策略**：制定明确的记忆清理策略，避免历史数据堆积

### 4.5 外部 AI 服务依赖风险

Claude-Mem 高度依赖外部 AI 服务（Claude、Gemini 等），**这些服务的稳定性和成本问题**可能影响系统的正常运行。

主要风险包括：



* **服务可用性**：外部 AI 服务可能出现宕机、限流等问题，影响记忆的生成和检索

* **响应延迟**：特别是对于中国用户，访问境外服务可能面临超过 1 秒的延迟，长连接可能被中间设备中断，高峰期丢包严重

* **成本控制**：AI 服务按 token 计费，大规模使用可能导致成本失控

* **服务变更**：AI 服务提供商可能调整 API 接口或定价策略，影响系统兼容性

针对这些风险，可以采取以下应对措施：



* **多服务备份**：配置多个 AI 服务提供商，如同时使用 Claude 和 Gemini，实现故障转移

* **本地缓存**：对常用的记忆摘要进行本地缓存，减少对远程服务的依赖

* **成本监控**：设置 token 使用上限，定期监控成本支出

* **异步处理**：将 AI 处理任务异步化，避免阻塞主流程

* **降级策略**：设计优雅的降级方案，当外部服务不可用时仍能提供基本功能

对于**间歇性推进的个人项目**，Claude-Mem 的价值更加明显。即使中间停了两周，开发者回来后也不需要全靠自己翻 Git commit 和脑补。系统会自动提供相关的历史上下文，包括之前的设计决策、遇到的问题和解决方案。

在处理**大规模复杂项目**时，Claude-Mem 的优势更加突出。实际测试表明，处理 20 万 tokens 的复杂编程任务时，系统能精准记住数月前的代码架构；跨周重启项目不用重新梳理，AI 直接调用历史记忆快速衔接。这种能力对于维护大型代码库、参与长期项目的开发者来说，无疑是一个巨大的生产力提升。

### 5.2 团队协作：高效的知识共享平台

### 6.2 安装步骤

/plugin marketplace add thedotmack/claude-mem

```
/plugin install claude-mem
```

**Step 3：重启生效**

安装完成后，重启 Claude Code 使插件生效：



```
/quit
```

### 6.3 基本使用方法

#### 6.3.1 配置文件说明

Claude-Mem 的配置文件位于`~/.claude-mem/settings.json`，初次运行时会自动生成默认配置。以下是主要配置项说明：



```
{

&#x20; "CLAUDE\_MEM\_PROVIDER": "claude", // AI引擎：claude/gemini/openrouter

&#x20; "CLAUDE\_MEM\_MODEL": "claude-sonnet-4-5", // 具体模型

&#x20; "CLAUDE\_MEM\_CONTEXT\_OBSERVATIONS": 50, // 每次注入的观察数量（1-200）

&#x20; "CLAUDE\_MEM\_WORKER\_PORT": 37777, // Worker服务端口

&#x20; "CLAUDE\_MEM\_LOG\_LEVEL": "INFO", // 日志级别：DEBUG/INFO/WARN/ERROR/SILENT

&#x20; "CLAUDE\_MEM\_PYTHON\_VERSION": "3.13", // Python版本

&#x20; "CLAUDE\_MEM\_CONTEXT\_SHOW\_LAST\_SUMMARY": false, // 是否包含上次会话摘要

&#x20; "CLAUDE\_MEM\_CONTEXT\_SHOW\_LAST\_MESSAGE": false, // 是否包含上次最后消息

&#x20; "CLAUDE\_MEM\_SKIP\_TOOLS": \[ // 跳过这些工具的观察

&#x20;   "ListMcpResourcesTool",

&#x20;   "SlashCommand"

&#x20; ]

}
```

#### 6.3.2 核心操作命令

**1. 记忆搜索（mem-search 技能）**

使用自然语言搜索历史记忆，支持多种搜索模式：



```
mem-search "关于数据库迁移的讨论"

mem-search type:bugfix "认证相关问题"

mem-search filename:auth.ts

```
// 第一步：搜索索引（返回紧凑列表，约50-100 tokens/条）

timeline(observation\_id=123, depth\_before=3, depth\_after=3)

// 第三步：获取完整详情（仅对需要的ID调用，约500-1000 tokens/条）

get\_observations(ids=\[123, 456])
```

**3. 主动记忆（save\_memory）**

手动记录重要信息：



```
save\_memory(text="API requires auth header X-API-Key", title="API认证要求")

### 6.4 常见问题与解决方案

**Q1：安装后没有生效怎么办？**

A：确保已重启 Claude Code；检查终端输出是否有错误信息；查看`~/.claude-mem/logs`目录中的日志文件。

**Q2：搜索结果不准确怎么办？**

A：调整检索阈值；使用更精确的搜索关键词；检查记忆记录的标签是否正确；清理不相关的历史记录。

**Q3：token 消耗还是很高怎么办？**

A：确认是否正确使用了三层检索工作流；检查是否有不必要的自动注入；调整`CLAUDE_MEM_CONTEXT_OBSERVATIONS`参数；启用 Endless Mode（Beta 功能）。

**Q4：遇到兼容性问题怎么办？**

A：确保使用最新版本的 Claude Code；检查插件版本是否为最新；在 GitHub 上查看是否有已知问题；联系社区寻求帮助。
