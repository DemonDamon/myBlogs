# Superpowers Skills 使用场景指南

本文档详细说明每个 Superpowers 技能的使用场景和触发条件。

## 📋 技能分类

### 🎯 核心工作流技能（按开发流程顺序）

#### 1. **brainstorming** - 头脑风暴与设计
**使用时机：**
- ✅ 开始任何新功能开发之前
- ✅ 创建新组件、添加功能、修改行为之前
- ✅ 需要探索用户意图、需求和设计时
- ✅ 重构代码前需要重新设计架构时

**工作流程：**
1. 理解当前项目状态（文件、文档、最近提交）
2. 逐个提问细化想法（一次一个问题）
3. 提出 2-3 种方案并分析权衡
4. 分段呈现设计（每段 200-300 字）
5. 保存设计文档到 `docs/plans/YYYY-MM-DD-<topic>-design.md`

**典型场景：**
- "我想添加一个用户认证功能"
- "需要重构这个模块"
- "如何设计这个 API？"

---

#### 2. **using-git-worktrees** - 创建隔离工作区
**使用时机：**
- ✅ 开始新功能开发需要隔离工作区时
- ✅ 执行实施计划前创建独立环境
- ✅ 需要同时处理多个分支时

**工作流程：**
1. 检查现有 worktree 目录（`.worktrees` 或 `worktrees`）
2. 创建新的 worktree 到指定目录
3. 验证创建成功并切换到新工作区

**典型场景：**
- "为这个功能创建一个独立的工作区"
- "在执行计划前先创建 worktree"

---

#### 3. **writing-plans** - 编写实施计划
**使用时机：**
- ✅ 有规格说明或需求文档后
- ✅ 需要将设计转化为详细实施步骤时
- ✅ 在开始编码之前

**工作流程：**
1. 创建详细的实施计划
2. 将任务分解为 2-5 分钟的小步骤
3. 为每个任务指定：文件路径、代码、测试、验证命令
4. 保存到 `docs/plans/YYYY-MM-DD-<feature-name>.md`
5. 提供执行选项（子代理驱动 vs 并行会话）

**典型场景：**
- "基于设计文档创建实施计划"
- "将这个功能分解为可执行的任务"

---

#### 4. **executing-plans** - 执行计划（并行会话）
**使用时机：**
- ✅ 有书面实施计划需要执行时
- ✅ 在**单独的会话**中批量执行任务
- ✅ 需要在检查点进行审查时

**工作流程：**
1. 加载并审查计划
2. 批量执行任务（默认前 3 个）
3. 在批次间报告进度并等待审查
4. 继续下一批次

**典型场景：**
- "在新会话中执行这个计划"
- "批量实现这些任务"

---

#### 5. **subagent-driven-development** - 子代理驱动开发
**使用时机：**
- ✅ 在当前会话中执行实施计划
- ✅ 计划中的任务相对独立
- ✅ 需要快速迭代和审查

**工作流程：**
1. 为每个任务分派新的子代理
2. 每个任务完成后进行两阶段审查：
   - 第一阶段：规范符合性审查
   - 第二阶段：代码质量审查
3. 继续下一个任务

**vs executing-plans：**
- 同会话 vs 并行会话
- 每个任务后立即审查 vs 批次间审查
- 更快迭代 vs 批量处理

**典型场景：**
- "在当前会话中执行这个计划"
- "使用子代理逐个完成任务"

---

#### 6. **test-driven-development** - 测试驱动开发
**使用时机：**
- ✅ 实现任何新功能之前
- ✅ 修复 bug 之前
- ✅ 重构代码时
- ✅ 修改行为时

**核心原则：**
1. 先写失败的测试
2. 运行测试确认失败
3. 写最少的代码使测试通过
4. 重构代码

**典型场景：**
- "实现这个功能"（必须先写测试）
- "修复这个 bug"（先写重现测试）

---

#### 7. **systematic-debugging** - 系统化调试
**使用时机：**
- ✅ 遇到任何 bug、测试失败或意外行为时
- ✅ **在提出修复方案之前**
- ✅ 时间紧迫时（系统化比猜测更快）
- ✅ 已经尝试多次修复失败时

**核心原则：**
```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

**四个阶段：**
1. **根因调查**：读取错误信息、重现问题、检查最近变更、追踪数据流
2. **模式分析**：找到工作示例、对比参考实现、识别差异
3. **假设与测试**：形成单一假设、最小化测试、验证结果
4. **实施修复**：创建失败测试、实施单一修复、验证修复

**典型场景：**
- "这个测试失败了"
- "程序行为异常"
- "构建失败"

---

#### 8. **dispatching-parallel-agents** - 调度并行代理
**使用时机：**
- ✅ 面临 2+ 个独立任务时
- ✅ 任务没有共享状态或顺序依赖
- ✅ 可以并行工作时

**典型场景：**
- "有多个不相关的测试失败"
- "需要同时处理多个独立功能"
- "多个子系统有不同的问题"

---

#### 9. **requesting-code-review** - 请求代码审查
**使用时机：**
- ✅ 完成任务后
- ✅ 实现主要功能后
- ✅ 合并到主分支之前
- ✅ 子代理驱动开发中每个任务后（强制）

**工作流程：**
1. 获取 git SHA（BASE 和 HEAD）
2. 分派代码审查子代理
3. 审查规范符合性和代码质量
4. 根据反馈修复问题

**典型场景：**
- "请审查这段代码"
- "合并前需要审查"

---

#### 10. **receiving-code-review** - 接收代码审查反馈
**使用时机：**
- ✅ 收到代码审查反馈后
- ✅ **在实施建议之前**
- ✅ 反馈不清楚或技术上可疑时

**核心原则：**
- 验证后再实施
- 询问而非假设
- 技术正确性优先于社交舒适

**工作流程：**
1. 完整阅读反馈（不立即反应）
2. 用自己的话重述需求（或询问）
3. 对照代码库实际情况验证
4. 评估：技术上是否合理？
5. 回应：技术确认或有理由的反对
6. 实施：一次一个，每个都测试

**典型场景：**
- "收到代码审查反馈，如何处理？"
- "这个建议是否合理？"

---

#### 11. **verification-before-completion** - 完成前验证
**使用时机：**
- ✅ 声称工作完成之前
- ✅ 提交代码或创建 PR 之前
- ✅ 声称问题已修复之前

**核心原则：**
```
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
```

**工作流程：**
1. 识别：什么命令能证明这个声明？
2. 运行：执行完整命令（全新、完整）
3. 检查：输出是否符合预期？
4. 声明：只有验证通过才能声明完成

**典型场景：**
- "功能完成了"（必须先运行测试验证）
- "bug 修复了"（必须先验证）

---

#### 12. **finishing-a-development-branch** - 完成开发分支
**使用时机：**
- ✅ 实施完成，所有测试通过
- ✅ 需要决定如何整合工作时
- ✅ 准备合并或创建 PR 时

**工作流程：**
1. 验证测试通过
2. 呈现选项：
   - 直接合并到主分支
   - 创建 Pull Request
   - 清理和归档
3. 执行选择的操作
4. 清理临时文件

**典型场景：**
- "功能完成了，如何合并？"
- "所有测试通过，下一步做什么？"

---

### 🛠️ 工具与辅助技能

#### 13. **using-superpowers** - 使用技能系统
**使用时机：**
- ✅ 开始任何对话时
- ✅ 需要了解如何使用技能时

**核心原则：**
- 如果认为有 1% 的可能性某个技能适用，**必须**调用该技能
- 在响应或行动之前调用相关技能

**技能优先级：**
1. 流程技能优先（brainstorming, debugging）
2. 实施技能其次（frontend-design, mcp-builder）

---

#### 14. **writing-skills** - 编写技能
**使用时机：**
- ✅ 创建新技能时
- ✅ 编辑现有技能时
- ✅ 验证技能是否有效时

**核心原则：**
- 技能编写 = 测试驱动开发应用于流程文档
- 先看失败（基线行为），再写技能，再看通过

**典型场景：**
- "创建一个新技能"
- "改进这个技能"

## 🔄 典型开发流程

### 场景 1：新功能开发
```
1. brainstorming → 探索需求和设计
2. using-git-worktrees → 创建隔离工作区
3. writing-plans → 编写详细实施计划
4. subagent-driven-development → 执行计划（当前会话）
   或 executing-plans → 执行计划（并行会话）
5. test-driven-development → 每个任务都遵循 TDD
6. requesting-code-review → 每个任务后审查
7. verification-before-completion → 完成前验证
8. finishing-a-development-branch → 完成分支
```

### 场景 2：修复 Bug
```
1. systematic-debugging → 系统化调试（必须）
2. test-driven-development → 先写重现测试
3. 实施修复
4. verification-before-completion → 验证修复
5. requesting-code-review → 审查修复
```

### 场景 3：处理多个独立问题
```
1. dispatching-parallel-agents → 并行处理
2. 每个代理使用 systematic-debugging
3. 完成后 verification-before-completion
```

### 场景 4：代码审查反馈
```
1. receiving-code-review → 接收并评估反馈
2. 验证反馈的技术合理性
3. 实施修复（一次一个）
4. verification-before-completion → 验证
```

## ⚠️ 重要原则

### 必须使用的场景
- **任何创意工作前** → `brainstorming`
- **任何 bug 修复前** → `systematic-debugging`
- **任何功能实现前** → `test-driven-development`
- **声称完成前** → `verification-before-completion`

### 禁止跳过的场景
- ❌ "这个 bug 很简单，不需要系统化调试"
- ❌ "先快速修复，再写测试"
- ❌ "功能完成了"（没有运行验证）

### 技能组合使用
- `brainstorming` → `writing-plans` → `executing-plans` 或 `subagent-driven-development`
- `systematic-debugging` → `test-driven-development` → `verification-before-completion`
- `subagent-driven-development` + `requesting-code-review`（每个任务后）

## 📚 快速参考

| 技能 | 触发条件 | 核心原则 |
|------|---------|---------|
| brainstorming | 任何创意工作前 | 探索需求 → 设计方案 → 文档化 |
| writing-plans | 有需求后，编码前 | 分解为 2-5 分钟的小任务 |
| executing-plans | 有书面计划，并行会话 | 批量执行 + 检查点审查 |
| subagent-driven-development | 有书面计划，当前会话 | 子代理 + 两阶段审查 |
| test-driven-development | 任何实现前 | 先写失败测试 → 最小实现 → 重构 |
| systematic-debugging | 任何 bug 前 | 先找根因，再修复 |
| requesting-code-review | 完成任务后 | 审查规范 + 代码质量 |
| receiving-code-review | 收到反馈后 | 验证 → 评估 → 实施 |
| verification-before-completion | 声称完成前 | 运行验证命令，看输出 |
| finishing-a-development-branch | 测试通过后 | 验证 → 选项 → 执行 |

---

## 💡 提示

1. **技能会自动触发**：如果 AI 认为某个技能适用，会自动使用
2. **可以明确请求**：可以说"使用 brainstorming 技能"来强制使用
3. **技能可以组合**：多个技能可以按顺序使用
4. **遵循流程**：不要跳过必要的技能步骤
